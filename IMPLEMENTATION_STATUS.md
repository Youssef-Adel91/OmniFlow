### Real PDF report generation — 2026-09-23

- Replaced the placeholder in [`vault_worker/generator.py`](omniflow-backend/src/ai_workers/vault_worker/generator.py) (was `f"OmniFlow AI Report: ...".encode("utf-8")` saved with a `.pdf` extension) with a genuine PDF built by the new [`pdf_builder.py`](omniflow-backend/src/ai_workers/vault_worker/pdf_builder.py) module, populated with real data pulled from the database at generation time: the tenant's `business_name`, the customer's `display_name`/`unified_phone` (queried live via `get_tenant_session`), the price paid, the transaction reference, the report type, and the generation timestamp. Any additional metadata keys on the payment event (e.g. a future deed number) render as extra report fields without code changes.
- **This went through three real, user-caught rounds before landing — recorded in full because each round found a genuine defect the previous self-check missed, not a flaky retest:**
  1. **First version (fpdf2 + manual `arabic_reshaper`/`python-bidi`):** self-check only verified PDF structural validity (header/trailer/size), never what was actually on the page. User caught it visually: Arabic letters rendered disconnected, and every row after the tenant name was missing from the page entirely (present in the raw byte stream, off-canvas — `multi_cell`'s default `new_x=XPos.RIGHT` leaves the cursor at the right edge of the previous line instead of resetting to the left margin).
  2. **Second version (fpdf2 + real HarfBuzz shaping via `set_text_shaping()`, cursor bug fixed):** fixed both visual bugs — verified by rasterizing and eyeballing a full realistic report. User then asked for the specific, correct test: does the PDF's actual **text layer** (not the picture of it) survive `pdftotext`/select-all? It did not. Investigation (downloaded real poppler `pdftotext`, installed `pikepdf`/`pdfminer.six`/`uharfbuzz` for direct inspection) found a real, reproducible fpdf2 bug: `TTFFont.shape_text` builds a HarfBuzz-cluster-to-source-character map and `.pop()`s each cluster the first time a glyph consumes it, so any glyph sharing a cluster with another (routine for Arabic — e.g. a base+mark pair) gets silently dropped from the PDF's `/ToUnicode` CMap. Confirmed against fpdf2 2.8.8 **and** an unreleased git-master build (commit `4287c924`, which does fix a related-but-different bug — [py-pdf/fpdf2#1952](https://github.com/py-pdf/fpdf2/issues/1952), the 100-entries-per-`bfchar`-block limit — but not this one). Effect: ~15-20% of glyphs on a page this size render perfectly on screen but are unextractable — garbled or missing on copy/paste, search, or a screen reader. A post-processing patch (`pikepdf`-based, filling the gaps with an explicit `U+FFFD` per missing code) reduced but did not eliminate the problem.
  3. **Final version:** rather than keep patching fpdf2/HarfBuzz internals, switched the whole PDF backend to **WeasyPrint** (HTML/CSS → PDF via Pango). Independently re-verified with real `pdftotext` (poppler, downloaded and run directly — not a Python wrapper) and `pdfminer.six` (a spec-literal ToUnicode-CMap extractor, unlike PyMuPDF which appears to reverse-engineer text from the embedded font directly and therefore doesn't actually exercise the `/ToUnicode` CMap this check cares about): **zero missing or incorrect characters, zero `U+FFFD` placeholders.** Also found and fixed one WeasyPrint-specific defect along the way: the mandatory lam-alef ligature ("لا") swapped its two source characters on extraction (`"الاختبار"` → `"االختبار"`), reproduced identically by both `pdftotext` and `pdfminer.six`, independent of PyMuPDF; fixed with `font-feature-settings: "liga" 0, "rlig" 0, "calt" 0, "clig" 0` in the stylesheet, which disables ligature fusion (still correctly joined, contextual Arabic letterforms — just without that one typographic flourish) and removes the bug entirely.

### Concurrency audit — conversation counters, takeover races, SSE ordering (item 13) — 2026-09-24

Audited every write path touched by two agents/workers racing on the same row: `message_count`, agent takeover, user provisioning, SSE publication timing, and the AI-reply-vs-human-takeover window. Four real races confirmed, two already safe, one narrowed but not closed.

**1. `Conversation.message_count` — real lost-update race, fixed.** `ConversationRepository.add_message()` did `conv.message_count = (conv.message_count or 0) + 1` in Python (read-modify-write): two concurrent inserts on the same conversation could both read the same starting value and both write `N+1`, silently losing one increment. Replaced with a single atomic `UPDATE conversations SET message_count = message_count + 1 WHERE conversation_id = :id` — the increment now happens inside Postgres, not in application code. `Customer.engagement_score` was also audited: no writer exists anywhere in the codebase (only read in `broadcast_worker`, `tasks.py`, `dashboard.py`), so there is no race to fix there — it's simply unimplemented.

**2. Takeover/ownership double-assign — real race, fixed.** `ConversationRepository.assign_agent()` used to read `assigned_agent_id`, then unconditionally write the caller's id — two agents clicking "take over" within milliseconds could both read `NULL` and both write, with whichever commit landed last silently winning; the loser got a false 200 OK and only discovered the truth on their next `send_message` (a 409). Replaced with a single atomic conditional `UPDATE ... SET assigned_agent_id = :agent, status = 'human_active' WHERE assigned_agent_id IS NULL OR assigned_agent_id = :agent`. Postgres itself is now the arbiter: at most one concurrent UPDATE can match on an unassigned row. A new `ConversationConflictError` is raised when `rowcount == 0` and the conversation is genuinely owned by someone else (distinguished from "not found" via `get_or_404`), mapped to a real HTTP 409 `{"code": "ALREADY_ASSIGNED"}` by a new exception handler in `gateway/main.py`.

**3. SSE published before the transaction commits — real race, fixed.** `gateway/routers/conversations.py`'s three endpoints (`send_message`, `takeover_conversation`, `return_to_ai`) called `_publish_sse_event()` inline in the endpoint body — before the FastAPI dependency-injected session's surrounding `async with get_tenant_session(...)` block actually commits (which only happens when the dependency generator tears down, after the endpoint function returns). A subscriber could receive an event for a row a concurrent fresh read still couldn't see. Fixed by moving all three publishes onto FastAPI `BackgroundTasks`, which Starlette only runs after the response has been prepared — strictly after the session dependency's commit. (Note: `persistence.py`'s own SSE call sites for `persist_inbound_message`/`persist_outbound_message`/`update_message_delivery_status` were already audited and confirmed correct — they already sit after their own `get_tenant_session` block exits.)

**4. AI-reply-after-takeover — real TOCTOU window, narrowed, not closed.** `outbound_dispatcher/worker.py` checked `load_conversation_state()` once, then had a real async gap (credential resolution, Redis idempotency lookup, a DB persist) before actually calling the WhatsApp send — if a human took over during that gap, a stale AI reply could still go out. Added a second `load_conversation_state()` re-check immediately before the network call, narrowing the window to just the WhatsApp API round-trip itself. **This is not a full fix** — a complete fix needs a lock or fencing token on the conversation, which was judged out of scope for this pass. `semantic_router/worker.py` and `llm_invoker/worker.py` use the same one-shot check pattern upstream of routing/generation, not upstream of the actual send, so a stale routing/generation decision there just produces a queued outbound message that still has to pass through `outbound_dispatcher`'s (now double) check before anything reaches WhatsApp — left unchanged.

**5. Already safe, no change needed.** User-provisioning races (`webhooks.py::_handle_user_created`) already use an optimistic insert inside a `SAVEPOINT`, relying on a real DB-level `unique=True` constraint on `TenantUser.clerk_id`; the losing request's `IntegrityError` is caught and it returns a benign "already provisioned" 200.

**Verified with real concurrent Postgres connections (not asyncio tasks sharing one session) and real Redis pub/sub** — new script: [`scripts/validate_concurrency_races.py`](omniflow-backend/scripts/validate_concurrency_races.py), ran twice. Scenario A: 8 genuinely concurrent `assign_agent` calls (each its own connection, real `TenantUser` FK rows) on the same unassigned conversation — exactly 1 wins, the other 7 get a real `ConversationConflictError`, and the DB ends up owned by exactly one agent. Scenario B: 20 genuinely concurrent `add_message` calls — `message_count` ends up exactly 20, matching the real row count (a lost update would show fewer). Scenario C: the real `takeover_conversation` endpoint function with a real `BackgroundTasks` — confirms a real Redis subscriber receives **nothing** while the transaction is still open, and only receives the event (with the row already durably committed and visible on a fresh read) after the background task is actually run.

**Not covered by the validation script** (explicitly, not silently): the item-4 TOCTOU narrowing in `outbound_dispatcher` needs a real Kafka + WhatsApp-transport-boundary harness to exercise end-to-end under actual concurrent load; it was verified by code inspection and the existing 37-test unit suite (all still passing) only, not by a dedicated real-dependency race drill.

Backend suite: 37/37 tests still pass after all four fixes.

### Fencing token for the AI-reply-after-takeover race (LAUNCH_READINESS_PROMPT item 13's residual risk) — 2026-09-27

Per the client's explicit instruction to keep working top-down through open, no-credential-needed items and to review my own work critically before calling it finished — which is exactly what happened here, including a real self-correction worth recording in full.

**What was actually broken, precisely**: `outbound_dispatcher`'s only defense against a stale AI reply was re-checking `Conversation.status != AI_ACTIVE` with a fresh SELECT immediately before dispatch. That check is blind to one real, concrete scenario: a human takes over a conversation, reads/replies to the customer, then hands it back to AI (`return_to_ai`) — all while an AI reply generated *before* the takeover is still working through the pipeline. By the time that stale reply reaches the pre-send check, `status` reads `AI_ACTIVE` again, so the check waves it through, even though a human already handled this conversation with context the stale reply never had.

**First draft of the fix overclaimed what it did — caught and corrected before shipping, not after.** My first pass described this as "closing the TOCTOU race" and "no matter how small the gap." On rereading my own reasoning critically, that was wrong: the gap between the *final* pre-send check and the actual outbound HTTP call to WhatsApp/Instagram is **not** closeable by any database-only mechanism, atomic or not — no compare-and-swap can make an external network call conditional on a DB row in one atomic step, and neither provider supports recalling an already-sent message. I had conflated "a more textbook-correct primitive" (atomic UPDATE...WHERE...RETURNING vs. a plain SELECT-then-branch) with "closes the race," which it does not, for that specific sliver. I rewrote every comment, docstring, and this section to say precisely what the fix does and does not do, instead of shipping the inflated version.

**What it actually, verifiably does**: new `Conversation.ai_reply_epoch` column (migration `0017_conv_ai_reply_epoch`), bumped atomically by every human takeover (`repository.assign_agent`, in the same atomic UPDATE that already handles the agent-assignment race) — and, critically, **never reset by `return_to_ai`**, unlike `status`. An AI reply captures the live epoch value (`load_conversation_state`, extended with this one field) right before calling the LLM; `outbound_dispatcher`'s pre-send check is now `UPDATE conversations SET updated_at = now() WHERE conversation_id = :id AND ai_reply_epoch = :captured`, and aborts if that affects zero rows. Because the epoch only ever increases, a stale captured value correctly fails to match even after the conversation has cycled back to `AI_ACTIVE` — closing exactly the hole described above. The PDPL `is_processing_restricted` check (a different, Customer-level flag) is preserved unchanged alongside this, not replaced by it.

**Verified against real Postgres, through the real production entry points** — new script [`scripts/validate_ai_reply_epoch_fencing.py`](omniflow-backend/scripts/validate_ai_reply_epoch_fencing.py), run against the real `OutboundDispatcherWorker.process_message()` and the real `ConversationRepository.assign_agent()`/`update_status()` (not reimplementations), run twice:
1. No takeover: a captured epoch matching the live value dispatches normally.
2. Exact repro of the hole: a real takeover then a real return-to-ai run after the epoch was captured — confirmed `status` is back to `AI_ACTIVE` (so a status-only check would see nothing wrong) while `ai_reply_epoch` has permanently moved to `1`. Feeding the stale captured epoch into the real dispatcher correctly blocks the send (mocked WhatsApp call NOT invoked) and leaves the message `FAILED`.
3. **Regression proof, not just assertion**: re-ran scenario 2's exact stale message with `ai_reply_epoch=None`, forcing the dispatcher down the old fallback branch (the plain status-only check, i.e. exactly what shipped before this fix) — confirmed that branch **incorrectly sends** the same stale reply. This proves the epoch check in scenario 2, not some unrelated guard, is what actually catches it.
- The pre-existing `validate_concurrency_races.py` (agent-assignment race) and `validate_kafka_outbound_recovery.py` (crash/DLQ drill) were re-run against the changed code and still pass unchanged — confirmed no regression in either.
- Full backend suite (37 tests) passes throughout. Migration applied and round-tripped (downgrade → upgrade) against the real running Postgres in this container, not just written.

**What this explicitly does NOT cover, disclosed rather than left implicit**: the gap between the pre-send check and the actual network call (see above — irreducible with these providers); the AI worker's own self-escalation path (`llm_invoker` setting `status=ESCALATED` on repeated LLM failure) does not bump the epoch — that's the worker's own decision about its own message, not a race with a *different* in-flight reply, so it was left out of scope rather than padding the change; multi-replica/horizontal-scaling races are not a concern here since Kafka partitions outbound messages by tenant+phone, so all messages for one conversation are already processed in order by a single consumer instance.

### Instagram/Messenger webhook had no signature verification — found and fixed — 2026-09-28

The client asked me to audit every place `META_WEBHOOK_HMAC_SECRET` (or any variable holding the same value) is used in the code, to confirm a secret rotation actually took effect everywhere, not just in one place. The direct answer, and what the audit turned up:

**Where `META_WEBHOOK_HMAC_SECRET` is actually consumed — exactly one place**: `channel_adapters/whatsapp/security.py`, loaded once from `settings.meta_webhook_hmac_secret` at module import time, used only to verify the WhatsApp webhook's `X-Hub-Signature-256` header. No hardcoded copies of the value exist anywhere in source (consistent with the earlier full-repo `detect-secrets` sweep and the earlier full-git-history sweep, both zero matches) — it's sourced from `Settings` in the one place that uses it, so rotating it in `.env`/the real deployment's environment is sufficient on its own for that one consumer. A previous session already found and fixed a *different* bug in this area (a duplicate `META_WEBHOOK_HMAC_SECRET=` line in `.env`, second silently shadowing the first) — re-confirmed during this audit that only one line exists now, that bug hasn't regressed.

**A separate, confusingly-similar field exists and is dead**: `Settings.meta_app_secret` (`META_APP_SECRET` in `.env`) is declared but never read anywhere in `src/` — currently `mock` in both `.env` and `.env.example`. Not a live risk (nothing consumes it, so a stale value there doesn't matter), but worth knowing it is *not* what protects anything, in case it gets wired up later without realizing it's currently a placeholder.

**The real finding — a genuine security gap, unrelated to rotation, fixed regardless**: the Instagram/Messenger webhook (`channel_adapters/instagram/router.py`, `POST /api/v1/webhooks/meta`) had **no signature verification of any kind**. Its own docstring said so explicitly ("no HMAC needed for this adapter") — which is incorrect: Meta signs every webhook delivery for an App with the same App Secret regardless of which product (WhatsApp, Instagram, Messenger) triggered it, exactly like the WhatsApp adapter's own docstring states. This meant anyone who found the webhook URL could POST a fabricated payload — a fake inbound DM, a fake page comment — and have it processed as a genuine Meta event (persisted, published to Kafka, and answered by the AI), completely independent of whether the HMAC secret was ever rotated, because nothing was checking it on this endpoint at all.

**Fixed**: added the same `X-Hub-Signature-256` check the WhatsApp adapter already had, reusing the existing generic `shared/security/hmac_verify.verify_hmac_signature()` utility (not a copy-pasted reimplementation) against the same `settings.meta_webhook_hmac_secret`. Rejects with HTTP 403 before any logging or parsing of the payload — an unsigned request isn't confirmed to be from Meta, so it gets no different treatment than a malicious one.

**Verified against the real app, not a reimplementation** — new [`scripts/validate_instagram_webhook_signature.py`](omniflow-backend/scripts/validate_instagram_webhook_signature.py), booting the real `create_app()` through a real ASGI transport and hitting the real `/api/v1/webhooks/meta` route:
1. No signature header → 403 `INVALID_SIGNATURE`.
2. Well-formed but wrong signature → 403.
3. A signature that's genuinely valid *for a different payload* (tampered body, same header) → 403 — proves the check verifies the actual bytes received, not just "a signature was present."
4. A correctly computed HMAC-SHA256 signature over the real payload → 200, reaches normal processing.

All four pass. Full backend suite (37 tests) still passes unchanged. This has zero test coverage before this fix (no existing test or validator touched the Instagram router at all), which is likely why it went unnoticed.
